## 输出通用桌面端 Computer Use 技术方案

任务来源：

- 对应任务 ID：Computer Use 技术方案。
- 触发原因：用户明确要求不要为微信做专属开发，而是参考 GenericAgent，规划通用的真实电脑操作能力，并先输出 Markdown 技术方案。

为什么这样开发：

- 原有 `browser_ocr_real_input_fallback_design.md` 偏向浏览器 OCR 和系统输入兜底，不适合作为通用桌面操作总方案。
- GenericAgent 的经验表明，真实电脑操作的关键不是直接点击坐标，而是窗口枚举、PID 激活、AX 控件树、视觉降级和动作验证。
- Cohert 需要保持 Go 工具边界清晰，把 macOS PyObjC / Quartz / AX 细节隔离到 helper，而不是把底层 API 直接暴露给模型。

技术路径：

- 新增独立设计文档，明确 M1 只读桌面感知、M2 受限输入、M3 视觉控件候选三个阶段。
- 将安全规则前置：真实输入必须绑定 PID、先激活目标窗口、必要时 `ask_user` 确认、动作后验证。
- 将坐标空间显式化：区分 `screenshot-local`、`window-logical`、`window-physical`、`screen-physical`。

关键改动：

- 新增 `docs/desktop_computer_use_technical_design.md`。

最终效果：

- Cohert 后续桌面端能力有了不绑定具体应用的技术路线。
- 第一阶段开发目标收敛为 `desktop_permissions`、`desktop_windows`、`desktop_activate`、`desktop_screenshot`、`desktop_ax_snapshot`、`desktop_ocr`。
- 后续受限输入和视觉控件候选有明确边界和验收标准。

验证方式：

- 检查 Markdown 文档结构、工具命名、实施顺序和安全边界是否覆盖当前已确认约束。

后续影响：

- 下一步若开始编码，应优先实现 M1 只读桌面感知，并同步补 `sops/desktop_sop.md`。

## 创建 Cohert Go CLI MVP

任务来源：

- 对应任务 ID：MVP 初始化。
- 触发原因：项目需要从命令行核心能力开始，先做一个可运行的 Go 版本 Agent Runtime，UI 和全局安装暂缓。

为什么这样开发：

- 用户当前更关注命令行核心能力，不希望一开始引入 UI、安装器或复杂工程脚手架。
- Go 适合做单二进制 CLI，后续如果要做类似 Claude Code 的全局命令，迁移成本较低。
- MVP 阶段先跑通 Agent 主链路，比提前做过多外围能力更重要。

技术路径：

- 使用 Go module 搭建最小项目。
- 使用 `main.go` 支持在项目根目录直接执行 `go run .`。
- 使用 `cmd/cohert/main.go` 保留标准 CLI 二进制入口，方便后续 `go build -o cohert ./cmd/cohert`。
- 按职责拆分为 `internal/cli`、`internal/app`、`internal/agent`、`internal/llm`、`internal/tools`。

关键改动：

- 新增 CLI 入口和根入口。
- 新增 Agent Runner。
- 新增 OpenAI-compatible LLM Client。
- 新增基础工具注册体系和文件/命令/询问类工具。
- 新增 `configs/config.yaml` 默认配置读取逻辑。

最终效果：

- 可以在项目根目录执行 `go run .` 进入交互模式。
- 可以执行 `go run . ask "任务"` 运行单次任务。
- Cohert 具备最小 Agent Loop：用户输入、模型流式输出、工具调用、工具结果回灌、继续下一轮。

验证方式：

- 本地启动主程序。
- 使用 DeepSeek API Key 运行真实命令行任务。
- 通过 `go test ./...` 验证当前 Go 包可编译。

后续影响：

- 后续 P0/P1 开发都围绕这个 CLI-first Runtime 继续扩展。
- UI、全局安装、复杂会话管理都不在 MVP 初始化阶段处理。

## 统一项目命名和文档口径

任务来源：

- 对应任务 ID：项目品牌和文档清理。
- 触发原因：项目需要作为独立项目 Cohert 存在，文档和描述中不能留下旧项目痕迹。

为什么这样开发：

- 项目名称、命令名、文档描述必须统一，否则后续用户理解和安装命令都会混乱。
- 独立项目需要自己的表述，不应该让 README 和学习文档看起来像迁移说明。

技术路径：

- 将项目描述统一为 Cohert。
- 删除文档中关于旧项目、重写来源、临时命名的描述。
- 将启动方式统一为 `go run .` 和 `go run . ask "任务"`。
- 暂不做全局命令安装，避免把未确认方案写进用户文档。

关键改动：

- 更新 `README.md`。
- 更新 `docs/learning.md`。
- 更新 `docs/testing.md`。
- 保留 `cmd/cohert` 作为正式命令入口。

最终效果：

- 用户看到的是一个独立的 Cohert 项目。
- 本地测试文档只描述当前已经实现的启动方式。
- 全局启动方案没有进入当前文档，避免误导。

验证方式：

- 检查文档中的项目命名和启动命令。
- 确认 `go run .` 可以从项目根目录启动。

后续影响：

- 后续所有新增文档、代码注释、命令输出都应使用 Cohert 这个名称。

## 补齐运行状态和工具名常量

任务来源：

- 对应任务 ID：P0-001、P0-002。
- 触发原因：运行状态和工具名原本散落在代码中，后续维护容易拼错，也不利于测试稳定识别。

为什么这样开发：

- Agent 的运行状态属于核心协议，不应该用裸字符串到处写。
- 工具名是模型调用工具时的关键标识，必须集中管理。
- 常量集中后，后续新增工具、重命名工具、写测试都会更稳。

技术路径：

- 在 `internal/agent/types.go` 定义运行状态常量。
- 在 `internal/tools/registry.go` 定义工具名常量。
- 替换 Runner 和工具注册里的裸字符串。

关键改动：

- 新增 `RunStatusDone`。
- 新增 `RunStatusExited`。
- 新增 `RunStatusMaxTurnsExceeded`。
- 新增 `ToolNameFileRead`、`ToolNameFileWrite`、`ToolNameFilePatch`、`ToolNameCodeRun`、`ToolNameAskUser`。

最终效果：

- Runner 返回状态时使用常量。
- 工具注册和 unknown tool 提示使用统一工具名。
- 后续测试可以直接对常量断言。

验证方式：

- 执行 `go test ./...`。
- 运行主程序确认状态常量替换没有破坏流程。

后续影响：

- 新增工具时必须先补工具名常量，再注册工具。
- 新增运行状态时必须先在 `internal/agent/types.go` 定义。

- tool_calls 分片拼接有单元测试保护。

## 统一工具错误返回格式

任务来源：

- 对应任务 ID：P0-030、P0-032。
- 触发原因：工具失败、未知工具、坏 JSON 参数需要用稳定结构回灌给模型，帮助模型自我修正。

为什么这样开发：

- 如果工具错误只是普通字符串，模型很难稳定识别错误类型和下一步动作。
- 测试也很难基于普通字符串做准确断言。
- 统一结构可以同时服务模型、日志和单元测试。

技术路径：

- 在 `internal/agent/types.go` 定义 `ToolErrorData`。
- 使用 `status/code/message/hint` 作为统一错误结构。
- 在 Runner 参数解析失败时返回 `bad_json`。
- 在工具执行失败时返回 `tool_run_failed`。
- 在工具不存在时返回 `unknown_tool` 和可用工具列表。

关键改动：

- 新增 `ToolStatusSuccess`、`ToolStatusError`。
- 新增 `ToolErrorData`。
- 新增 `NewToolError`。
- 修改 Runner 中的 bad JSON 处理逻辑。
- 修改工具和 registry 的错误返回。

最终效果：

- 工具错误变成可机器识别的结构化数据。
- 模型看到错误后能根据 `hint` 重新生成参数或选择正确工具。
- 坏 JSON 不再静默变成空参数。

验证方式：

- 执行 `go test ./...`。
- 检查 Runner 中 bad JSON 分支会回灌结构化错误。

后续影响：

- 后续所有工具错误都应优先返回 `ToolErrorData`。
- 新增错误类型时要补明确的 `code` 和中文 `hint`。

## 定义 Session 数据结构和本地存储层

任务来源：

- 对应任务 ID：P0-010、P0-011。
- 触发原因：后续需要支持会话列表和恢复上下文，必须先定义本地 session 数据结构和文件路径约定。

为什么这样开发：

- Runner 当前只有内存 `history`，进程退出后上下文会丢失。
- 要实现 resume，必须先决定 session 元信息和消息历史分别怎么存。
- `meta.json` 和 `history.jsonl` 分开，可以让会话列表读取更快，也让消息追加更简单。

技术路径：

- 新建 `internal/session` 包。
- 定义 `Session` 保存会话元信息。
- 定义 `HistoryEntry` 保存单条消息历史。
- 定义 `Store` 统一管理目录和路径。
- 默认目录使用 `temp/sessions`，避免 MVP 阶段写入全局 HOME。

关键改动：

- 新增 `internal/session/types.go`。
- 新增 `internal/session/store.go`。
- 新增 `internal/session/store_test.go`。
- 定义 `DefaultRootDir`、`MetaFileName`、`HistoryFileName`。
- 定义 `NewID` 生成带时间前缀的 session ID。

最终效果：

- 可以创建 session 目录。
- 可以写入 `meta.json`。
- 可以稳定计算 `history.jsonl` 路径。
- session 字段和后续 resume 需要的数据结构已经确定。

验证方式：

- 执行 `go test ./...`。
- 单测验证 `Store.Create` 会写入 `meta.json`。
- 单测验证 `HistoryPath` 的路径约定稳定。

后续影响：

- 后续 P0-012 可以直接基于 `Store` 写入 `history.jsonl`。
- 后续 P0-014 可以基于 `HistoryEntry` 恢复 `Runner.history`。

## Runner 写入 history.jsonl

任务来源：

- 对应任务 ID：P0-012。
- 触发原因：Runner 已经有内存 `history`，但还没有把 user/assistant/tool 消息落盘，无法支持进程退出后的上下文恢复。

为什么这样开发：

- 会话恢复的基础是完整保存每一轮消息。
- 写入时机必须靠近 Runner 追加内存 history 的位置，否则容易出现“内存有、文件没有”的不一致。
- Runner 不应该自己拼路径和写 JSON 文件，文件组织交给 `session.Store`。

技术路径：

- 在 `session.Store` 中新增 `AppendHistory`，负责追加一行 `HistoryEntry` 到 `history.jsonl`。
- 在 `session.Store` 中新增 `LoadMeta`，用于刷新和读取 session 元信息。
- 在 `agent.Runner` 中新增 `SessionStore`、`SessionCWD`、`SessionModel`、`sessionID`。
- 在 Runner 中新增 `appendMessage`，统一维护内存 history 和本地 history。
- 在 Runner 第一次收到用户输入时创建 session，后续同一个 Runner 复用同一个 session。
- 在 `app.NewRunner` 中默认注入 `temp/sessions` 存储。

关键改动：

- 更新 `internal/session/store.go`。
- 更新 `internal/agent/runner.go`。
- 更新 `internal/app/app.go`。
- 新增 `internal/agent/runner_test.go`。
- 更新 `internal/session/store_test.go`。

最终效果：

- 每次用户输入会写入一条 `role=user` 历史。
- 模型最终回答会写入一条 `role=assistant` 历史。
- 模型调用工具时，assistant 的 `tool_calls` 消息会先写入。
- 每个工具执行结果会写入一条 `role=tool` 历史。
- `history.jsonl` 使用一行一个 JSON，方便追加和后续读取恢复。

验证方式：

- 执行 `gofmt`。
- 执行 `go test ./...`。
- `internal/session` 测试验证 `AppendHistory` 会写入 JSONL。
- `internal/agent` 测试验证 Runner 执行后会生成 `meta.json` 和 `history.jsonl`。

后续影响：

- P0-014 可以继续读取 `history.jsonl`，把消息还原进 `Runner.history`。
- P0-013 可以读取 `meta.json` 和 `history.jsonl` 行数实现 session list。
- `/clear` 当前会清空内存 history 并重置 sessionID，后续如果要保留旧 session，需要再设计清理语义。

## 重写开发任务拆解表

任务来源：

- 对应任务 ID：开发计划调整。
- 触发原因：原来的 `development_task_breakdown.md` 把很多能力平均铺开，`doctor` 被放进最优先 10 项，但实际运行中更紧急的问题是 `code_run` 卡死、命令越界、session 只能写不能恢复。

为什么这样开发：

- 开发计划应该跟真实问题对齐，不能只按功能清单机械排序。
- GA 的 `code_run` 有一些值得借鉴的经验，例如 `bash -c`、stdout 流式读取、timeout、输出截断。
- GA 也有不足，例如没有强制 command guard、没有杀进程组、不能阻止模型在脚本里 `cd /Users/...`。
- Cohert 当前要优先补命令执行安全和 session resume，而不是先做 doctor。

技术路径：

- 重新阅读 `docs/development_task_breakdown.md` 的现有任务。

## 按 GA 思路稳住 code_run 执行器

任务来源：

- 对应任务 ID：P0-060、P0-061、P0-062、P0-063、P0-064、P0-065、P0-066。
- 触发原因：用户在交互模式里询问 session 效果时，模型调用 `code_run` 执行了大范围递归搜索，导致终端长时间卡住；同时 `bash -lc` 加载了用户 shell 配置，输出了 `.bashrc` 中 `tldr completion bash` 的崩溃噪音。

为什么这样开发：

- 用户明确要求先照 GA 的 `code_run` 思路做，不要在 tool 调用外面额外加一层 command guard。
- 当前阶段优先把执行器本身做稳，比提前抽象安全策略更直接。
- GA 的 `code_run` 使用 `bash -c`、默认 60 秒 timeout、输出截断，这些点适合 Cohert 借鉴。
- Cohert 保留自己的结构化结果优势，把 timeout 作为字段返回，而不是只写到 stdout。

技术路径：

- Unix/macOS 下把 `bash -lc` 改成 `bash -c`。
- 保留 60 秒默认 timeout。
- 增加最大 timeout 上限 120 秒，避免模型传入超长 timeout。
- Unix/macOS 下为命令创建独立进程组。
- context 超时时通过 `cmd.Cancel` 杀掉整组进程。
- 超时结果中返回 `timeout`、`timeout_seconds` 和中文 `hint`。
- 增加 `code_run` 专项测试。

关键改动：

- 更新 `internal/tools/code_run.go`。
- 新增 `internal/tools/code_run_unix.go`。
- 新增 `internal/tools/code_run_windows.go`。
- 新增 `internal/tools/code_run_test.go`。
- 更新 `docs/development_task_breakdown.md`，把 command guard 后置。
- 更新 `docs/testing.md`，补充 code_run 行为和测试命令。

最终效果：

- `code_run` 在 Unix/macOS 下不会因为 `bash -lc` 加载用户启动文件。
- 长命令超时后会返回结构化结果。
- timeout 上限被限制到 120 秒。
- Unix/macOS 下超时时会尽量清理整组子进程。

## 实现 Context Manager 第一版

任务来源：

- 用户决定开始开发上下文管理模块，并指定按 `docs/context_management_design.md` 的阶段一推进。
- 阶段一目标是确定性请求前压缩，不引入模型摘要和自动 compact。

为什么这样开发：

- Cohert 已经能把完整对话写入 `history.jsonl` 并恢复到 `Runner.history`，但模型请求不能长期直接携带完整历史。
- 工具输出，尤其是 `code_run`、`file_read` 和后续浏览器工具，会快速撑大上下文。
- 完整历史和模型可见上下文必须分离：磁盘和内存保留完整消息，请求前只构造压缩后的 messages。
- 第一版选择规则压缩，成本低、行为确定、容易用单测锁定。

技术路径：

- 新增 `internal/contextmgr` 包，提供 `Config`、`Manager`、`BuildInput`、`BuildResult` 和 `Stats`。
- 实现工具结果 Micro Compact：
  - 只压缩旧的 `role=tool` 消息。
  - 最近若干条工具结果保持完整。
  - 超长工具结果按头尾保留，中间替换为 compact notice。
- 实现 tool-call group 裁剪：
  - `assistant tool_calls` 和对应 `tool` 结果作为一组保留或裁剪。
  - 裁剪时从最新 group 往前保留。
  - 孤立 `tool` 消息会从本轮请求中丢弃，并记录 warning。
- 在 `Runner` 中新增 `ContextManager` 字段。
- 将 `Runner.Run` 中直接复制 `r.history` 的位置改为 `buildRequestMessages()`。
- `appendMessage` 和 `SessionStore.AppendHistory` 仍然保存完整消息，不裁剪磁盘历史。
- 在 `app.Config` 中新增 `Context` 配置，并从 `configs/config.yaml` 的 `context:` 段读取。
- 在 `app.NewRunner` 中创建默认 `contextmgr.Manager`。
- 在 `/config` 和外部 `config` 命令中展示关键 context 配置。

关键改动：

- 新增 `internal/contextmgr/types.go`、`manager.go`、`budget.go`、`tool_result.go`、`trim.go`。
- 更新 `internal/agent/runner.go`，接入请求前上下文构造。
- 更新 `internal/app/config.go` 和 `internal/app/app.go`，接入默认配置和装配。
- 更新 `configs/config.yaml`，增加 `context:` 配置段。
- 更新 `internal/repl/repl.go` 和 `internal/cli/cli.go`，展示 context 配置。
- 新增 `internal/contextmgr/manager_test.go`。
- 新增 `internal/agent/runner_context_test.go`。
- 新增 `internal/app/config_test.go`。
- 更新 `docs/usage.md`。

最终效果：

- 长 session resume 后，完整历史仍保存在 `Runner.history` 和 `history.jsonl`。
- 模型请求前会经过 Context Manager。
- 旧的长工具结果不会完整进入后续模型请求。
- 历史过长时，会插入 context notice，并只保留最近的消息 group。
- tool-call 协议不会因为裁剪被拆坏。
- 第一版不调用模型做摘要，因此不会引入额外失败链路。

验证方式：

- 执行 `go test -v -gcflags="all=-l -N" ./internal/contextmgr ./internal/agent ./internal/app`。
- 执行 `go test ./...`。

后续影响：

- `/compact` 仍然可以在后续接入手动 Full Compact。
- 后续可以增加 `memory.md` 和 `compact.md` 注入，但不影响第一版确定性压缩。
- 浏览器工具接入前已经有请求前压缩兜底。

## 升级 slash 命令为选择菜单

任务来源：

- 用户明确要求按照 Claude Code 的交互方式处理 slash 命令。
- 之前版本只有 Tab 补全和 `/` 文本命令面板，仍然不够接近 Claude Code 的命令选择体验。

为什么这样开发：

- Claude Code 的 slash 命令体验重点不是“记住命令并手打”，而是用户输入 `/` 后能看到命令列表并选择。
- Cohert 当前已经有 `internal/repl` 层，适合继续在输入层增强，而不需要改 Agent Loop。
- 真实终端和管道输入需要分开处理：真实终端可以打开交互选择菜单，管道和测试环境必须继续保持纯文本可测试。

技术路径：

- 引入 `github.com/manifoldco/promptui`，用于真实终端里的上下键选择菜单。
- 当用户输入 `/` 时：
  - 如果是真实 TTY，打开 slash command select menu。
  - 如果不是真实 TTY，退化为文本命令面板。
- 菜单项包含命令写法和功能说明。
- 对 `/resume <id>` 这种需要参数的命令，选择后继续提示输入 session id。
- 保留 readline Tab 补全能力，用于用户已经输入命令前缀的场景。

关键改动：

- 更新 `internal/repl/repl.go`：
  - 新增 `slashMenuItem`。
  - 新增 `selectSlashCommand`。
  - 新增 `promptSessionID`。
  - `/` 从直接打印文本面板升级为真实终端选择菜单。
- 更新 `go.mod` 和 `go.sum`。
- 更新 `docs/usage.md` 和 `docs/testing.md`。

最终效果：

- 真实终端里输入 `/` 会打开命令选择菜单。
- 用户可以用上下键选择命令，按回车执行。
- `/resume` 选择后会继续要求输入 session id。
- 管道输入中 `/` 仍然输出文本命令面板，保证测试稳定。
- 已有 Tab 补全仍然保留。

验证方式：

- 执行 `go test ./...`。
- 执行 `printf '/\n/exit\n' | DEEPSEEK_API_KEY=dummy go run .`，验证非 TTY 回退行为。
- 真实菜单需要在终端中运行 `DEEPSEEK_API_KEY=dummy go run .` 后输入 `/` 手动验证。

## 实现浏览器 CDP 点击与输入链路

任务来源：

- 用户要求按以下顺序继续开发浏览器操作能力：
  - 插件 cdp command。
  - Go 层 `browser_cdp`。
  - `browser_click`。
  - `browser_click_element`。
  - `browser_type`。
  - `browser_type_element`。
  - 页面变化监控。
- 用户要求开发记录文档必须写清楚每一步的技术原因和实现方式。

为什么这样开发：

- 现有 Cohert 已具备 `browser_tabs`、`browser_open`、`browser_scan`、`browser_execute_js`，但只能读取页面和执行 JS。
- 普通 JS 的 `element.click()` 或 `dispatchEvent` 会产生 `isTrusted=false` 的合成事件，很多登录、支付、文件上传、自定义下拉框会拒绝这类事件。
- 浏览器真实交互应该走 CDP 的 `Input.dispatchMouseEvent`、`Input.insertText` 等输入协议。
- JS 仍然有价值，但它的职责应该是读取 DOM、滚动元素、计算 `getBoundingClientRect()`，而不是直接伪造点击。
- 如果动作工具只返回“success”，模型无法判断页面是否真的变化，容易重复点击或盲目继续，所以必须补轻量页面变化监控。

总体分层：

```text
模型工具调用
  -> internal/tools 解析和校验参数
  -> internal/browser.Client 稳定接口
  -> internal/browser.Bridge WebSocket 命令
  -> Chrome 插件 background.js
  -> chrome.debugger / chrome.scripting
  -> 用户真实 Chrome 标签页
```

### 第一步：插件 cdp command

开发内容：

- 在 `assert/cohert_browser_bridge/background.js` 中新增 `cdp` command。
- 新增 `withDebugger(tabId, fn)`，统一管理 `chrome.debugger.attach` 和 `detach`。
- 新增 `sendDebuggerCommand(target, method, params)`，封装 `chrome.debugger.sendCommand`。
- 新增 `handleCDP(request)`，负责解析 `method`、`params`、`tab_id` 并返回原始 CDP 结果。

关键实现：

```text
resolveTabId
  -> collectLightSnapshot
  -> chrome.debugger.attach
  -> chrome.debugger.sendCommand
  -> chrome.debugger.detach
  -> collectLightSnapshot
  -> buildLightDiff
```

为什么用 `finally detach`：

- Chrome debugger attach 后会占用 tab 的调试通道。
- 如果动作失败时不 detach，后续动作可能因为 debugger 状态异常而失败。
- detach 失败通常意味着 tab 已关闭或正在跳转，因此不能覆盖原始动作错误。

### 第二步：Go 层 browser_cdp

开发内容：

- 在 `internal/browser/types.go` 中新增 `CDPResult`。
- 在 `browser.Client` 接口中新增 `CDP` 方法。
- 在 `internal/browser/server.go` 中新增 `Bridge.CDP`，通过 WebSocket 发送 `command=cdp`。
- 在 `internal/browser/unavailable.go` 中补齐不可用客户端实现。
- 在 `internal/tools/browser_tools.go` 中新增 `BrowserCDP` 工具。
- 在 `internal/tools/registry.go` 和 `internal/app/app.go` 中注册 `browser_cdp`。

工具参数：

```json
{
  "tab_id": "可选",
  "method": "Runtime.evaluate",
  "params": {},
  "no_monitor": false
}
```

设计取舍：

- `browser_cdp` 不限制 method，因为它是底层调试工具。
- 常规点击和输入不鼓励直接使用 `browser_cdp`，否则模型容易拼错三段鼠标事件。
- 高频交互必须用更上层的 `browser_click` 和 `browser_type` 封装。

### 第三步：browser_click

开发内容：

- 在 `browser.Client` 中新增 `Click` 方法。
- 在 `Bridge` 中新增 `Click`，发送 `command=click`。
- 插件侧新增 `clickTab(request)`。
- 工具层新增 `BrowserClick`。

插件侧点击序列：

```text
Page.bringToFront
Input.dispatchMouseEvent mouseMoved(0, 0)
Input.dispatchMouseEvent mouseMoved(x, y)
Input.dispatchMouseEvent mousePressed(x, y, button=left, clickCount=1)
Input.dispatchMouseEvent mouseReleased(x, y, button=left, clickCount=1)
```

关键细节：

- `x/y` 是 viewport 坐标，不是屏幕物理坐标。
- 坐标来源应优先是 `getBoundingClientRect()`。
- 三个鼠标动作必须在同一次 debugger attach 生命周期内完成。
- 点击完成后短暂等待，再做轻量快照，用于判断页面是否变化。

为什么要有 `mouseMoved(0, 0)`：

- 首次 debugger attach 可能让 Chrome 出现调试提示条或触发布局变化。
- 预热动作可以让后续输入链路更稳定。
- 对 `browser_click_element` 来说，元素 rect 是在点击前即时测量的，因此不会长期复用旧坐标。

### 第四步：browser_click_element

开发内容：

- 工具层新增 `BrowserClickElement`。
- 新增 `locateElementRect`，通过 `browser_execute_js` 执行定位脚本。
- 定位脚本会执行 `querySelector`、`scrollIntoView`、`requestAnimationFrame`、`getBoundingClientRect`。
- Go 层计算中心点后调用 `client.Click`。

定位脚本的职责：

```text
找到 selector
滚动到 viewport 中央
等待一帧让布局稳定
读取 rect
检查 width/height/display/visibility
返回 rect
```

为什么不在 JS 里 click：

- JS click 是合成事件，`isTrusted=false`。
- 工具目标是模拟真实用户操作。
- 因此 JS 只负责“看”和“算”，CDP 负责“动”。

### 第五步：browser_type

开发内容：

- 在 `browser.Client` 中新增 `Type` 方法。
- 在 `Bridge` 中新增 `Type`，发送 `command=type`。
- 插件侧新增 `typeInTab(request)`。
- 工具层新增 `BrowserType`。

输入流程：

```text
Page.bringToFront
如果 clear=true：
  Input.dispatchKeyEvent Cmd+A
  Input.dispatchKeyEvent Backspace
Input.insertText(text)
```

为什么选择 `Input.insertText`：

- 它比 JS 直接设置 `value` 更接近真实输入。
- 对 React、Vue 等框架，真实输入链路更容易触发状态同步。
- 相比逐字符构造 keyDown/keyUp，`Input.insertText` 更简单稳定，适合第一版。

### 第六步：browser_type_element

开发内容：

- 工具层新增 `BrowserTypeElement`。
- 复用 `locateElementRect` 获取目标输入框 rect。
- 先调用 `client.Click(..., noMonitor=true)` 聚焦输入框。
- 再调用 `client.Type(..., noMonitor=用户参数)` 输入文本。

为什么聚焦点击不返回 diff：

- `browser_type_element` 是一个语义工具，用户关心的是“输入后页面变化”。
- 聚焦只是输入前置动作，如果也返回一段 diff，会让模型看到两段变化信号。
- 因此聚焦点击禁用监控，最终由输入动作统一返回 diff。

### 第七步：页面变化监控

开发内容：

- 插件侧新增 `collectLightSnapshot(tabId)`。
- 插件侧升级 `buildLightDiff(before, after)`。
- `execute_js`、`cdp`、`click`、`type` 都支持 `no_monitor`。

快照字段：

```text
tab.url
tab.title
当前可脚本化 tab 数量
document.body.innerText.length
可交互元素数量
document.activeElement 摘要
```

为什么只做轻量 diff：

- 完整 DOM diff 很容易产生巨大工具结果。
- 第一版目标是让模型知道动作是否生效，而不是重建网页结构。
- `browser_scan` 已经负责读取页面正文，动作工具只需要返回变化摘要。

返回示例：

```text
url changed
body text length 1024->1400
interactive elements 18->20
focus INPUT[name=q]->BUTTON
tab count 1->2
```

关键改动：

- 更新 `assert/cohert_browser_bridge/background.js`：
  - 新增 `cdp` command。
  - 新增 `click` command。
  - 新增 `type` command。
  - 新增 debugger attach/detach 封装。
  - 新增轻量页面变化快照和 diff。
- 更新 `internal/browser/types.go`：
  - 新增 `CDPResult`、`Point`、`Rect`、`ClickResult`、`ElementClickResult`、`TypeResult`、`ElementTypeResult`。
  - 扩展 `Client` 接口。
- 更新 `internal/browser/server.go`：
  - 新增 `CDP`、`Click`、`Type`。
- 更新 `internal/browser/unavailable.go`：
  - 补齐新接口的不可用实现。
- 更新 `internal/tools/browser_tools.go`：
  - 新增 `BrowserCDP`、`BrowserClick`、`BrowserClickElement`、`BrowserType`、`BrowserTypeElement`。
  - 新增 selector 定位和 rect 解析逻辑。
- 更新 `internal/tools/registry.go`：
  - 新增工具名常量。
  - 新增 schema 辅助函数。
  - 调整工具 schema 输出顺序。
- 更新 `internal/tools/args.go`：
  - 新增 float 和 object 参数解析。
- 更新 `internal/app/app.go`：
  - 注册新浏览器工具。
  - 更新系统提示词，让模型优先使用 DOM/JS 定位和 CDP 输入。
- 更新测试：
  - `internal/browser/server_test.go` 覆盖 `cdp`、`click`、`type` WebSocket 命令。
  - `internal/tools/browser_tools_test.go` 覆盖 `browser_cdp`、`browser_click`、`browser_type` 工具调用。
- 更新 `docs/ga_browser_technical_route.md`：
  - 记录浏览器输入链路落地状态。

最终效果：

- Cohert 已具备从“读取页面”到“真实点击和输入”的第一版闭环。
- selector 点击和 selector 输入遵循“JS 定位、CDP 动作”的边界。
- 动作工具会返回轻量页面变化摘要。
- OCR 仍然只作为后续兜底，不进入普通网页主链路。

验证方式：

- 执行 `node --check assert/cohert_browser_bridge/background.js`，验证插件脚本语法。
- 执行 `go test ./...`，验证 Go 编译、工具注册、bridge mock 和已有模块。

后续影响：

- 可以继续补真实浏览器端到端验证页面，例如本地 HTML 表单页面，测试 `browser_click_element` 和 `browser_type_element`。
- 可以继续扩展 `browser_wait_for_text`，让登录、搜索、跳转后的等待更显式。
- 可以考虑在 `browser_click_element` 中增加重测坐标机制，应对首次 debugger attach 造成的布局偏移。
- iframe、文件上传、截图 OCR、下载策略、CSP fallback 仍然不属于第一版主链路。

## 实现浏览器等待链路

任务来源：

- 用户反馈 Cohert 有时打开网页后，网页还没加载出来，Agent 就开始改方案，体验很差。
- 这个问题的根因不是“不会打开网页”，而是缺少“打开后等待页面到位”的工具链路。

为什么这样开发：

- 现代网页大量内容由前端 JS 异步渲染。
- `chrome.tabs.create` 或 `chrome.tabs.update` 返回后，页面可能还在白屏、骨架屏、loading 或局部请求中。
- 即使 `tab.status == complete`，SPA 页面也可能还在继续渲染正文和结果列表。
- 如果 Agent 在这些状态下立刻 `browser_scan`，就会读到半成品页面，然后误判“没有结果”“没有按钮”“页面打不开”，进而换方案。

目标行为：

```text
错误链路：
browser_open -> browser_scan -> 页面没出来 -> 误判 -> 改方案

正确链路：
browser_open -> browser_wait_for_load -> browser_wait_for_stable -> browser_scan
```

点击或输入后的正确链路：

```text
browser_click_element / browser_type_element
  -> browser_wait_for_selector / browser_wait_for_text / browser_wait_for_stable
  -> browser_scan 或继续操作
```

### 第一步：插件 wait command

开发内容：

- 在 `assert/cohert_browser_bridge/background.js` 中新增统一 `wait` command。
- 新增 `sleep(ms)`，用于插件侧轮询。
- 新增 `normalizeWaitTiming(request)`，统一处理 `timeout_ms` 和 `interval_ms`。
- 新增 `readPageState(tabId)`，读取页面轻量状态。
- 新增 `waitForCondition(tabId, timing, check)`，统一轮询骨架。
- 新增四个具体等待实现：
  - `waitForLoad`
  - `waitForSelector`
  - `waitForText`
  - `waitForStable`
- 在 `handleCommand` 中接入 `command === "wait"`。

为什么等待放在插件侧：

- 插件能直接调用 `chrome.tabs.get(tabId)` 读取 `tab.status`。
- 插件能通过 `chrome.scripting.executeScript` 读取页面 DOM。
- 如果 Go 侧轮询，每次检查都要经过 WebSocket 请求，延迟和协议复杂度更高。
- wait 作为一个插件 command 返回一次结果，更适合模型理解。

为什么 timeout 不直接抛错：

- 超时不一定是系统错误，也可能只是页面没有出现目标状态。
- 返回 `status: "timeout"` 能让模型知道“已经等过了但没等到”。
- 真正的协议错误仍然通过 WebSocket error 返回，例如 tab 不可用、selector 参数为空。

### 第二步：browser_wait_for_load

用途：

- 等页面基础加载完成。
- 主要放在 `browser_open` 后，或者点击链接导致页面跳转后。

判断条件：

```text
chrome.tabs.get(tabId).status == complete
document.readyState == interactive 或 complete
```

返回字段：

```json
{
  "status": "success",
  "mode": "load",
  "matched": true,
  "ready_state": "complete",
  "tab_status": "complete",
  "url": "...",
  "title": "..."
}
```

解决的问题：

- 页面还在白屏时不要扫描。
- 页面刚跳转时不要立刻判断失败。
- 打开搜索页、文档页、登录页后先等基础 DOM 到位。

### 第三步：browser_wait_for_selector

用途：

- 等某个元素出现、可见、隐藏或消失。

参数：

```json
{
  "tab_id": "可选",
  "selector": ".result-item",
  "state": "attached|visible|hidden|detached",
  "timeout_ms": 10000,
  "interval_ms": 200
}
```

状态含义：

```text
attached  querySelector 能找到元素
visible   元素存在，rect 宽高大于 0，且 display/visibility/opacity 可见
hidden    元素存在但不可见
detached  querySelector 找不到元素
```

解决的问题：

- 搜索结果列表还没渲染时，不要判断“没有结果”。
- 弹窗还没关闭时，不要继续点击后面的按钮。
- 按钮还没出现时，不要直接改用别的策略。

### 第四步：browser_wait_for_text

用途：

- 等页面正文中出现某段文字。

参数：

```json
{
  "tab_id": "可选",
  "text": "提交成功",
  "timeout_ms": 10000,
  "interval_ms": 200
}
```

适合场景：

- 等“登录成功”。
- 等“提交成功”。
- 等“验证码已发送”。
- 等搜索结果关键词出现。

为什么它和 selector 都需要：

- 有些页面结果没有稳定 selector，但有明确文案。
- 有些页面文案可能变化，但结构 selector 稳定。
- 两者互补，模型可根据任务选择。

### 第五步：browser_wait_for_stable

用途：

- 等页面轻量状态稳定一段时间。
- 这是不知道该等哪个 selector 或 text 时的通用兜底。

判断字段：

```text
tab status
document.readyState
url
title
body.innerText.length
可交互元素数量
```

参数：

```json
{
  "tab_id": "可选",
  "stable_ms": 800,
  "timeout_ms": 10000,
  "interval_ms": 200
}
```

设计取舍：

- 不比较完整 DOM，避免性能和返回内容过大。
- 不要求正文完全不变很久，默认只需要短时间稳定。
- 这是 scan 前的稳定性保险，不替代 `browser_scan`。

### 第六步：Go 层 Wait 接口

开发内容：

- 在 `internal/browser/types.go` 中新增 `WaitResult`。
- 在 `browser.Client` 中新增 `Wait` 方法。
- 在 `internal/browser/server.go` 中新增 `Bridge.Wait`。
- 在 `internal/browser/unavailable.go` 中补齐不可用实现。
- 将 `defaultCommandTimeout` 调整为更长时间，避免 wait 工具本身还没超时，Go bridge 先超时。

为什么使用一个底层 `Wait` 接口：

- 插件协议只需要一个 `command=wait`。
- Go 工具层可以拆成多个语义工具。
- 后续新增 `browser_wait_for_url` 时，可以复用同一个底层接口。

### 第七步：Go 工具层四个语义工具

为什么不直接暴露一个 `browser_wait`：

- 工具描述可以明确写出使用场景。

## 浏览器主链路强化：点击、输入、URL 等待、截图

### 强化 browser_click_element

旧实现：

```text
querySelector
scrollIntoView
getBoundingClientRect
取中心点
browser_click
```

问题：

- 中心点可能被浮层、固定 header、透明遮罩覆盖。
- 滚动后只测一次 rect，复杂页面可能布局尚未稳定。
- 失败时只能知道元素找不到或不可见，无法知道是否被谁挡住。

新实现：

```text
querySelector
scrollIntoView
等待两帧 requestAnimationFrame
重测 rect
检查 display / visibility / opacity / pointer-events
检查 disabled / aria-disabled
生成多个候选点击点
用 elementFromPoint 做遮挡检查
选中第一个真正命中目标元素或其子元素的点
再走 CDP 真实点击
点击后执行短 stable wait
```

候选点包括：

```text
中心点
左中 / 右中
上中 / 下中
四个角附近安全点
```

返回增强：

- `clicked_at` 返回实际点击点。
- `hit` 返回命中的元素摘要。
- `diff` 附带自动短等待结果。

### 强化 browser_type_element

旧实现：

```text
定位元素 rect
点击中心点聚焦
browser_type 输入
```

新实现：

```text
复用强化后的元素定位和遮挡检查
要求目标必须是 input / textarea / select / contenteditable
点击可命中的候选点聚焦
CDP 输入文本
回读 value / innerText / textContent
补发 input/change 事件
返回 actual 和 verified
```

校验规则：

```text
clear=true  -> actual 必须等于目标文本
clear=false -> actual 包含目标文本即可
```

这样可以让模型知道“工具调用成功”和“页面真实接收输入”是不是一回事。


用途：

- 读 SOP 后提醒模型提炼关键点。
- 多轮任务后提醒模型重读 SOP。

## 浏览器高层交互工具：browser_press_key 与 browser_snapshot

## 收敛浏览器工具面：对齐 GA 的 JSON 命令路由

任务来源：

- 用户指出 `browser_cdp` 暴露给模型后，模型会反复调用同一个底层工具，自己手写 `Runtime.evaluate`、`Input.dispatchKeyEvent`、`Input.dispatchMouseEvent` 等 CDP 命令。
- 用户要求参考 GA 的做法，不要继续堆很多浏览器工具。

GA 的做法：

```text
公开工具：
web_scan
web_execute_js

内部能力：
普通 JS
CDP
tabs
cookies
batch
management
contentSettings
```

关键点：

- GA 底层有 CDP，但没有把 `web_cdp` 作为公开工具给模型。
- `web_execute_js` 的 `script` 如果是普通 JS，就进入页面执行。
- `web_execute_js` 的 `script` 如果是 JSON 字符串且带 `cmd`，插件就把它当内部命令路由。

### 第一步：实现 `browser_execute_js` JSON 命令识别

开发内容：

- 在 `assert/cohert_browser_bridge/background.js` 中新增 `parseExecuteJSCommand(script)`。
- 如果 `script` 是对象，且含 `cmd` 或 `command`，直接作为内部命令。
- 如果 `script` 是字符串，先尝试 `JSON.parse`。
- 只有解析结果是对象且含 `cmd` 或 `command` 时，才走内部路由。
- 其他内容仍然按普通 JS 执行。

判断逻辑：

```text
普通 JS：
document.title
return document.body.innerText

JSON 命令：
{"cmd":"tabs"}
{"cmd":"cdp","method":"Runtime.evaluate","params":{"expression":"document.title"}}
```

为什么这样做：

- 保持 `browser_execute_js` 的原有能力。
- 不让 JSON 命令被误当作页面 JS 执行。
- 让 CDP 高级能力藏在 `browser_execute_js` 后面，减少模型看到的工具数量。

### 第二步：插件内部命令路由

开发内容：

- 新增 `handleExecuteJSCommand(command, parentRequest)`。
- 新增 `handleRoutedCommand(message)`。
- `handleCommand` 中除 `execute_js` 外，其余命令复用 `handleRoutedCommand`。

当前路由支持：

```text
tabs
scan
open
cdp
click
type
wait
batch
```

路由链路：

```text
browser_execute_js
  -> script 是 JSON command
  -> handleExecuteJSCommand
  -> handleRoutedCommand
  -> handleCDP / clickTab / typeInTab / waitInTab / handleBatch
```

设计细节：

- 如果 JSON 命令没有 `tab_id/tabId`，会继承外层 `browser_execute_js` 的 `tab_id/tabId`。
- 如果 JSON 命令没有 `no_monitor/noMonitor`，会继承外层参数。
- 禁止 JSON 路由递归调用 `execute_js`，避免内部循环。

### 第三步：增加简单 batch

开发内容：

- 在插件中新增 `handleBatch(message)`。
- 一次请求里顺序执行多个内部命令。
- 子命令默认继承外层 `tab_id/tabId`。
- 子命令失败不会中断整个 batch，而是把该项记为：

```json
{
  "status": "error",
  "command": "...",
  "error": "..."
}
```

第一版取舍：

- 只做顺序执行。
- 暂不实现 GA 的 `$N.path` 结果引用语法。
- 先解决“模型连续多轮调用底层工具”的问题，后续确实需要再补复杂引用。

### 第四步：Go 层避免包坏 JSON 命令

问题：

- Cohert 的 `normalizeBrowserScript` 会把简单表达式自动包成 `return (...)`。
- 如果不改，`{"cmd":"cdp"}` 会变成：

```text

```

这样插件就无法识别 JSON 命令。

开发内容：

- 在 `internal/tools/browser_tools.go` 中新增 `looksLikeBrowserJSONCommand(script)`。
- 使用 `json.Unmarshal` 判断脚本是否是 JSON 对象。
- 如果对象里含 `cmd` 或 `command`，直接原样返回，不自动包 `return`。

### 第五步：隐藏公开 `browser_cdp`

## 实现 browser_dom_summary DOM 摘要工具

任务来源：

- 对应任务 ID：Browser P0 DOM 摘要能力。
- 触发原因：`docs/browser_ocr_real_input_fallback_design.md` 的 P0 方案要求在截图/OCR 前先补一层 `browser_dom_summary`，借鉴 GA `simphtml.py` 的低噪声 DOM 摘要思路，减少普通网页任务过早进入 OCR 或系统输入。

为什么这样开发：

- Cohert 已经具备 `browser_scan`、`browser_snapshot`、`browser_execute_js`、CDP 点击/输入和截图能力，但 `browser_scan` 主要返回正文文本，`browser_snapshot` 主要返回可交互元素，二者都不适合稳定表达表单当前值、同源 iframe、open shadowRoot 和固定浮层。
- 直接进入 OCR 会引入 Python/OCR 依赖，并且会丢失 DOM 结构、selector、表单语义等可操作信息。
- 因此第一阶段先做 DOM 摘要，保持浏览器链路仍以 DOM/JS 为主：`scan/snapshot -> dom_summary -> screenshot/OCR`。

技术路径：

- 插件侧新增 `dom_summary` command，在页面 `MAIN` world 中遍历真实 DOM，但不修改页面。
- Go bridge 新增 `DOMSummary` 方法，仍通过现有 WebSocket request id 协议转发命令和解析结果。
- 工具层新增 `browser_dom_summary`，默认 `max_chars=20000`，并默认开启 iframe、shadow DOM、表单值和固定浮层摘要。
- 系统提示词增加使用顺序：当 `browser_scan/browser_snapshot` 不足但 DOM 仍可访问时，先用 `browser_dom_summary`，再考虑截图/OCR。

关键改动：

- `assert/cohert_browser_bridge/background.js`
  - 新增 `domSummaryTab`。
  - `handleRoutedCommand` 支持 `dom_summary`。
  - 摘要逻辑过滤 `script/style/meta/link/noscript/template/svg/canvas` 等高噪声节点。
  - 表单字段结构化返回 `selector/tag/type/name/id/placeholder/value/value_present/checked/disabled`。
  - password、hidden、token、secret、csrf、cookie、auth 等敏感字段不返回明文 value，只返回 `value_present`。
  - 同源 iframe 可读时合入摘要，跨域 iframe 只返回元数据。
  - open shadowRoot 可读时合入摘要，并统计 `shadow_roots`。
  - fixed/sticky 浮层可选摘要并统计 `fixed_overlays`。
- `internal/browser/types.go`
  - 新增 `DOMSummary`、`DOMFormSummary`、`DOMFieldSummary`、`DOMFrameSummary`。
  - `browser.Client` 接口新增 `DOMSummary(...)`。
- `internal/browser/server.go`
  - 新增 `Bridge.DOMSummary`，发送 `command=dom_summary`。
- `internal/browser/unavailable.go`
  - 新增不可用实现，保持 browser bridge 启动失败时错误路径一致。
- `internal/tools/browser_tools.go`
  - 新增 `BrowserDOMSummary` 工具和默认字符上限。
- `internal/tools/registry.go`
  - 新增 `ToolNameBrowserDOMSummary` 并加入 schema 顺序。
- `internal/app/app.go`
  - 注册 `NewBrowserDOMSummary`。
  - 更新中英文系统提示词中的浏览器操作顺序。
- `internal/browser/server_test.go`
  - 新增 bridge command payload 和返回解析测试。
- `internal/tools/browser_tools_test.go`
  - fake browser client 新增 `DOMSummary`。
  - 新增默认参数、显式选项和敏感字段不透出明文的测试。

最终效果：

- 模型可调用 `browser_dom_summary` 获取低噪声页面摘要。
- 对普通网页，Cohert 可以在 DOM 仍可访问时先读取结构化表单/iframe/shadowRoot 信息，而不是直接截图或 OCR。
- 密码、hidden token、secret/csrf/cookie/auth 类字段不会通过 DOM 摘要泄露明文。
- 插件 JSON 路由也支持 `{"cmd":"dom_summary"}`，可被 `browser_execute_js` 内部路由复用。

验证方式：

- 执行 `go test ./...`，验证 Go bridge、工具层、注册链路和既有包测试全部通过。

后续影响：

- 如果后续要接 GA 的 `batch $N.path` 或 CSP fallback，仍应保持底层高权限能力不默认暴露给模型。

## Runner 最终答复前强制长期记忆判断

任务来源：

- 对应任务 ID：Evolution Memory 收尾触发增强。
- 触发原因：飞书浏览器操作任务中，Runner 已经产生浏览器验证信号并给过长期记忆提示，但模型直接输出最终答复，没有调用 `start_long_term_update`，导致可复用操作经验没有进入沉淀判断流程。

为什么这样开发：

- 原逻辑只在下一轮注入 `[LONG-TERM MEMORY HINT]`，属于软提示。模型如果忽略提示并直接 final，Runner 会立刻结束。
- 经验沉淀不应该默认写入，但应该在有明显信号时强制模型做一次选择：要么启动 `start_long_term_update`，要么在后续 `memory_propose_update` 中 `skip=true`。
- 一次性任务事实、联系人、消息正文不能沉淀；真正应该沉淀的是浏览器/飞书操作流程、selector、验证策略等可复用经验。

技术路径：

- 在 `longTermMemorySignals` 中新增 `finalReviewPrompted`，防止模型忽略 review 后无限循环。
- 将长期记忆触发原因抽成 `longTermMemoryReasons(signals, turn)`，供普通 hint 和 final review 复用。
- 在 `Run` 的无 tool_calls 分支中，先把模型 final 文本写入 history，再调用 `maybeForceLongTermMemoryReview`。
- 如果存在长期记忆信号、尚未启动 `start_long_term_update`、还没做过 final review、并且还有下一轮 turn 预算，则追加 `[LONG-TERM MEMORY FINAL REVIEW]` 并继续下一轮。
- 如果已经到 `MaxTurns` 最后一轮，则不强行 review，避免把已经完成的任务变成 `max_turns_exceeded`。

关键改动：

- `internal/agent/runner.go`
  - 新增 `finalReviewPrompted`。
  - 新增 `maybeForceLongTermMemoryReview`。
  - 新增 `longTermMemoryReasons`。
  - final 分支在真正返回 `RunStatusDone` 前插入长期记忆 review 检查。
- `internal/agent/runner_context_test.go`
  - 新增 `TestRunnerForcesLongTermMemoryReviewBeforeFinal_BitsUT`。
  - 测试覆盖：浏览器工具成功后模型直接 final，Runner 会再发一轮 final review；随后模型调用 `start_long_term_update` 后任务正常结束。

最终效果：

- 长任务、浏览器验证、成功测试、用户明确要求记忆等场景下，模型不能再无声跳过长期记忆判断。
- Runner 不自动写长期记忆，只强制进入“是否沉淀”的显式判断流程。
- 对飞书这类一次性发送消息任务，系统会提示不要沉淀联系人和消息正文，只沉淀可复用操作经验。

验证方式：

- 执行 `go test ./internal/agent`。
- 执行 `go test ./...`。

后续影响：

- 后续可以继续增强 skip 闭环：如果模型判断无可复用经验，可以直接引导 `memory_propose_update skip=true`，让日志里也能看到显式 skip。
- 如果发现 final review 过于频繁，可以进一步收紧 `readReusableReference` 的浏览器工具触发条件，例如只对 `browser_dom_summary`、`browser_snapshot`、`browser_scan`、`browser_wait_*` 的组合触发。

## 对齐 GA SOP/Skill 体系并补齐 Memory SOP

任务来源：

- 用户要求系统研究 GenericAgent 的 SOP/skill 体系，并优化 Cohert 当前 SOP 流程、能力描述和等级划分。

参考结论：

- GA 的 Skill 不是单个插件概念，而是由原子工具、工作 checkpoint、L1/L2/L3/L4 记忆、专项 SOP/helper、后台反射共同形成。
- GA 的关键纪律是 “No Execution, No Memory”：长期记忆和 SOP 必须来自工具验证，不能把模型猜测、过程日志或一次性事实写成长期经验。
- GA 的计划/验证 SOP 很重，依赖成熟 subagent/task_dir 机制；Cohert 当前不应照搬强制多 agent 计划流，而应先做轻量、可执行、可审计的 SOP/记忆晋级链路。

为什么这样开发：

- Cohert 已经有 `start_long_term_update`、`memory_propose_update`、`memory_apply_update`、SOP candidate 和 `/sop promote`，但文档没有明确这些能力如何分级、何时使用、何时 skip。
- 原有 `sops/index.md` 只列文件，没有解释从工具能力到正式 Skill 的晋级标准。
- Runner SOP 路由没有覆盖长期记忆、SOP candidate、skill 和能力等级类任务，导致相关任务可能不会提示读取专门 SOP。

能力等级：

```text
C0 原子工具
  -> C1 SOP 约束
  -> C2 工作记忆
  -> C3 长期记忆 entry
  -> C4 SOP candidate
  -> C5 正式 SOP / Skill
```

关键改动：

- 新增 `sops/memory_sop.md`

## 实现 browser_ocr：受控 Python RapidOCR helper

任务来源：

- 用户要求先实现 OCR，并参考 GenericAgent 的实际实现。

参考结论：

- GA 的 `memory/ocr_utils.py` 使用 `rapidocr-onnxruntime`，返回全文、行文本、bbox 和置信度。
- 关键兼容点：RapidOCR 无文字时可能返回 `None`；置信度需要转为 float；默认不启用放大/高对比度预处理，避免损伤本来清晰的文字。
- Cohert 应继续保持 Go 主进程轻量，把 OCR 引擎隔离在 Python helper 内，通过稳定 JSON 协议交互。

为什么这样开发：

- Cohert 已有 `browser_screenshot`，但 DOM 不可读、canvas 或图片渲染文字时，模型缺少只读视觉文字兜底。
- OCR bbox 未来可以辅助浏览器坐标判断，但不能直接当系统屏幕坐标使用，因此第一版只读图、不执行鼠标键盘输入。
- Python 依赖不应在工具执行过程中隐式安装；缺依赖必须返回明确错误和安装提示。

关键改动：

- 新增 `scripts/browser_ocr.py`
  - 使用 `rapidocr-onnxruntime`、Pillow 和 NumPy。
  - 输入图片路径、最小置信度和可选 `enhance` 参数。
  - 输出单份 JSON：图片尺寸、全文、行文本、置信度、`[x1,y1,x2,y2]` bbox 和中心点。
  - 无文字时返回空 `lines`，不是错误。
  - 只在明确传入 `enhance=true` 时做对比度和放大预处理。
- 新增 `internal/vision/ocr_runner.go`
  - 用独立 Python 子进程运行 helper，默认超时 20 秒。
  - 解析并校验 helper JSON，限制异常输出大小。
  - 将缺依赖、超时、图片不可读、helper 缺失等情况映射为稳定错误码。
- 新增 `browser_ocr` 工具
  - 可读取 workspace 内图片；不传 `image_path` 时自动调用浏览器截图并保存。
  - 拒绝 workspace 外路径和通过符号链接逃出 workspace 的路径。
  - 限制返回行数和文本长度，bbox 显式标记为 `coordinate_space=screenshot-local`。
  - 注册到默认 Tool Registry，并加入系统提示词的 DOM 不可读兜底路径。
- 新增单元测试
  - 覆盖 helper JSON 解析、无效 bbox、结构化 helper 错误。
  - 覆盖 workspace 路径限制、自动截图、结果限长和缺依赖错误映射。
- 更新浏览器 SOP、README、使用/学习/测试文档和 GA 调研状态。

最终效果：

- Cohert 现在可以通过 `browser_ocr` 读取页面截图或 workspace 图片中的文字，并获得截图内 bbox。
- `browser_ocr` 不执行点击，不访问桌面窗口，不会绕过验证码或账号安全确认。
- 缺少 `rapidocr-onnxruntime`、Pillow 或 NumPy 时，工具会提示用户手动执行：

```bash
python3 -m pip install rapidocr-onnxruntime pillow numpy
```

验证方式：

- 执行 `python3 -m py_compile scripts/browser_ocr.py`。
- 用临时生成的 `HELLO OCR` 图片调用 helper，确认返回两行文字和 bbox。
- 执行 `go test ./...`。
- 执行 `go run . tools | rg '^browser_ocr$'`，确认工具已注册。

## 实现 M2.1：desktop_ax_press、风险确认与 AX 验证

任务来源：

- 对应任务 ID：Desktop Computer Use M2.1。
- 触发原因：用户确认先实现 `desktop_ax_press + 风险确认 + AX 结果验证`，在不开放坐标点击和键盘输入的前提下，先提供语义化桌面操作。

为什么这样开发：

- AXPress 直接作用于 Accessibility 元素，不依赖 Retina 坐标换算，稳定性和可审计性高于物理坐标点击。
- 普通 `confirm=true` 参数无法证明用户授权的是哪一个真实控件，因此确认必须绑定具体 PID、AX 节点和动作理由。
- AX 节点可能在快照后失效或重建，动作前后必须重新读取 AX 树，不能只信任旧 `node_id`。

技术路径：

- 扩展 `desktop.Driver` 和 macOS helper，增加 `ax_press` JSON 命令。
- helper 按 `ax:0/...` 节点路径重新定位控件，校验 PID 前台、role/title/description、enabled 和 `AXPress` action 后才执行。
- 新增进程内短时一次性确认令牌：`ask_user` 在用户明确回答“确认”后，按 `desktop_ax_press + pid + node_id + reason` 签发令牌；令牌不匹配、过期或重用都会失败。
- 新增风险分类：R1 可恢复动作直接执行，R2 外部副作用必须消费确认令牌，R3 支付/审批/授权/登录验证/删除等拒绝自动执行。
- `desktop_ax_press` 在动作前后读取受限 AX 快照；没有可观察树或目标节点变化时返回 `desktop_ax_press_unverified`，禁止盲目重试。

关键改动：

- 新增 `internal/tools/desktop_actions.go`、`internal/tools/confirmation.go`。
- 更新 `internal/desktop/types.go`、`internal/desktop/runner.go`、`scripts/desktop_darwin.py`。
- 更新 `internal/tools/ask_user.go`，支持受控 approval 与一次性 `confirmation_token`。
- 更新 Tool Registry、App 装配、桌面 SOP、技术方案和使用/学习/测试文档。
- 扩展桌面工具测试，覆盖 R1 成功验证、R2 令牌绑定和单次消费、R3 拒绝以及失效节点。

最终效果：

- Cohert 现在可对当前、语义匹配且支持 `AXPress` 的桌面 AX 节点执行受控语义点击。
- 外部副作用动作不会因模型传入普通布尔参数而绕过确认；确认令牌只能用于用户刚刚确认的唯一动作。
- 坐标点击、键盘输入和文本输入仍未开放。

验证方式：

- 执行 `python3 -m py_compile scripts/desktop_darwin.py`。
- 执行 `go test ./internal/desktop ./internal/tools ./internal/app -count=1`。
- 执行 `go run . tools | rg '^desktop_ax_press$'`，确认工具注册。
- 对当前前台 PID 调用 helper 的非法 node_id，确认返回 `desktop_ax_node_invalid` 且不触发真实 AXPress。
- 待执行 `go test ./... -count=1`。

后续影响：

## 实现 Skill Runtime 和 Claude Code 风格调用体验

任务来源：

- 用户要求 Cohert 支持 Claude Code-like Skills。
- 目标不是把 Skill 混成 MCP，而是实现一种可安装、可发现、可按需读取的工作流包机制。
- 用户随后要求能像 Claude Code 一样安装 Skill、用公开仓库测试、修复 Skill 流程中的用户确认问题，并补齐直接调用、更新和删除能力。

为什么这样开发：

- Skill 和 MCP 的边界不同：
  - MCP 是外部能力协议，核心是动态工具和外部服务连接。
  - Skill 是任务工作流包，核心是把某类任务的步骤、约束、模板和领域经验封装成 `SKILL.md`。
- 如果把所有 Skill 正文默认塞进 system prompt，会快速污染上下文，并且让无关 Skill 干扰模型判断。
- 因此采用“索引先行、正文按需读取”的设计：
  - 启动时只扫描 Skill 摘要。
  - System Prompt 只注入 Skill Index。
  - 任务命中时模型必须调用 `skill_read(skill_id)` 读取完整 `SKILL.md`。
  - 采用该工作流后用 `update_working_checkpoint` 保存 `related_skill` 和关键约束。
- 用户真实使用时还需要生命周期和直接调用体验，否则只能“自然语言要求按某个 Skill 做”，不够接近 Claude Code。

技术路径：

- 新增 `internal/skill`：
  - 扫描项目级 `.cohort/skills/<skill_name>/SKILL.md`。
  - 扫描用户级 `~/.cohert/skills/<skill_name>/SKILL.md`。
  - 生成稳定 ID：`project/<alias>` 或 `user/<alias>`。
  - 支持完整 ID 和唯一 alias 查找；同名 alias 同时出现在 project/user 时要求使用完整 ID，避免误读。
- 新增 `skill_read` 工具：
  - 只按 ID 读取目标 `SKILL.md`。
  - 限制最大读取字节数，返回 `truncated` 标记。
  - 读取后 Runner 会记录 pending skill read，并提醒模型如果采用该流程要更新 checkpoint。
- 更新 Runner 和系统提示：
  - `app.BuildSystemPrompt` 注入 Skill Index。
  - Skill Index 明确说明 Skill 不是 MCP，只是工作流包。
  - `Runner` 新增 `related_skill` 工作记忆字段。
  - 读取 Skill 后，若没有及时 `update_working_checkpoint`，下一轮追加系统提醒。

第一阶段能力：

- CLI：
  - `cohert skill list`
  - `cohert skill show <id>`
  - `cohert skill reload`
- REPL：
  - `/skill list`
  - `/skill show <id>`
  - `/skill reload`
- 文档：
  - 更新 `README.md`。
  - 更新 `docs/usage.md` 的 Skill Runtime 小节。

安装能力：

- 新增 `cohert skill install <path-or-git-url>`。
- 支持安装来源：
  - 本地 Skill 目录。
  - 本地 `SKILL.md` 文件。
  - git URL。
- 默认安装到项目级 `.cohort/skills`。
- 支持 `--scope user` 安装到 `~/.cohert/skills`。
- 支持 `--name <skill_name>` 从多 Skill 仓库中选择单个 Skill。
- 支持 `--force` 显式覆盖同名 Skill。
- 安装时只复制 Skill 包目录，不执行其中脚本，避免“安装即执行”的风险。
- git URL 走临时目录浅克隆，再按 `SKILL.md` 定位候选 Skill。

公开仓库验证：

- 使用公开仓库 `https://github.com/aslavchev/claude-code-skills.git` 测试。
- 因该仓库包含多个 Skill，执行：

```bash
go run . skill install --name commit https://github.com/aslavchev/claude-code-skills.git
```

- `go run . skill show project/commit` 能读取完整 Skill。

用户确认问题修复：

- 测试 `project/commit` 时发现一个交互问题：
  - Skill 要求 `$ARGUMENTS` 为空时询问用户选择要提交的文件。
  - 模型用普通文本问“你想把哪几个文件纳入这次 commit？”。
  - 但 REPL 在一次 `Runner.Run` 未结束前不会回到 `cohert ›` 输入点。
  - 随后长期记忆 final review 又在最终答复前续跑一轮，导致模型自己重复“刚才还在等你回答”。
- 根因：
  - Skill 中的 “ask user” 没有强制映射为 `ask_user` 工具。
  - `maybeForceLongTermMemoryReview` 不应打断正在等待用户回答的最终回复。
- 修复：
  - System Prompt 新增约束：缺少信息、授权或用户决策导致下一步无法继续时，必须调用 `ask_user`，不能只用普通文本提问。
  - Runner 新增 `awaitingUserInput` 判断；如果最终回复明显是在等待用户回答，则不插入长期记忆 final review。
  - 新增回归测试，覆盖“工具执行后最终回复询问用户选择文件”时不再继续下一轮。

调用体验增强：

- 新增 REPL 直接运行：

```text
/skill run <id> [arguments...]
```

- 新增 Claude Code 风格快捷调用：

```text
/<skill-alias> [arguments...]
```

- 快捷调用只对 `SKILL.md` frontmatter 中声明 `user-invocable: true` 的 Skill 生效，避免任意 Skill 抢占 slash 命令空间。
- 支持 `argument-hint`，在 `skill list` 中展示快捷命令参数提示。
- `/skill run` 和 `/<skill-alias>` 内部会生成普通任务，要求模型先 `skill_read` 对应 Skill，并设置 `related_skill`。

生命周期增强：

- 新增 CLI：
  - `cohert skill update <id> [path-or-git-url]`
  - `cohert skill uninstall <id>`
- 新增 REPL：
  - `/skill update <id> [path-or-git-url]`
  - `/skill uninstall <id>`
- 安装时写入 `.cohert-skill.json`，记录 source、scope、alias 和安装时间。

frontmatter 解析修复：

- 原解析器只支持 `key: value` 单行字段。
- 公开 Skill 常用 YAML folded scalar，例如：


  - `description: >` 折叠为单行描述。

  - `argument-hint: "[file1] [file2]"`。

## Skill Runtime 安全与质量层

任务来源：

- 用户确认继续实现 Skill safety/quality layer，并要求更新开发文档。
- 目标是在已有 Skill 安装/更新/删除/调用能力之上，补齐安装前预览、manifest hash/source metadata 和可复跑诊断命令。

为什么这样开发：

- Skill 是工作流包，不应在安装时执行任何脚本；安全边界应来自“只复制、可预览、可诊断”。
- 用户安装公开仓库或多 Skill 仓库前，需要先知道会安装哪个 Skill、写到哪里、文件数和内容摘要。
- 已安装 Skill 可能被手工编辑，`skill update` 也依赖 manifest source；缺少 manifest 或 hash 漂移时需要有清晰诊断，而不是等运行时才失败。

关键改动：

- 更新 `internal/skill/install.go`：
  - `InstallOptions` 新增 `DryRun`。
  - `InstallResult` 新增 `SourceType`、`WouldReplace`、`DryRun`、`ContentHash`。
  - 安装前统一计算 Skill 包普通文件 SHA256。
  - 正式安装写入 `.cohert-skill.json`，记录 `source`、`source_type`、`scope`、`alias`、`installed_at`、`content_hash`。
  - 复制 Skill 包时跳过来源里的旧 `.cohert-skill.json`，避免带入过期安装元数据。
- 新增 `internal/skill/doctor.go`：
  - `Store.Doctor(id)` 检查路径 scope、`SKILL.md` 可读性、frontmatter 质量、manifest 可读性、source/source_type 完整性和内容 hash 漂移。
  - 诊断结果分为 `ok`、`warn`、`error`，error 数量可用于 CLI 非零退出。
- 更新 `internal/cli/cli.go`：
  - 新增 `cohert skill install --dry-run <source>`。
  - 新增 `cohert skill doctor <id>`。
  - install/update 输出 source_type 和 hash。
- 更新 `internal/repl/repl.go`：
  - 新增 `/skill install [--dry-run] <source>`。
  - 新增 `/skill doctor <id>`。
  - 正式安装后 reload SkillStore 并刷新 system prompt；dry-run 不刷新、不写盘。
- 更新 `README.md` 和 `docs/usage.md`：
  - 补齐 Skill dry-run、doctor、manifest hash/source metadata 使用说明。

最终效果：

- 安装前可以先执行：

```bash
go run . skill install --dry-run ./path/to/skill
```

- 安装后可以执行：

```bash
go run . skill doctor project/<skill_name>
```

- 如果用户手工修改已安装 Skill，doctor 会报告 `content_hash` error，提示当前内容已经偏离安装 manifest。
