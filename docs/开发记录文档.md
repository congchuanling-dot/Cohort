## 创建 Cohert Go CLI MVP

任务来源：

- 对应任务 ID：MVP 初始化。
- 触发原因：项目需要从命令行核心能力开始，先做一个可运行的 Go 版本 Agent Runtime，UI 和全局安装暂缓。

为什么这样开发：

- 用户当前更关注命令行核心能力，不希望一开始引入 UI、安装器或复杂工程脚手架。
- Go 适合做单二进制 CLI，后续如果要做类似 Claude Code 的全局命令，迁移成本较低。
- MVP 阶段先跑通 Agent 主链路，比提前做过多外围能力更重要。

技术路径：

- 使用 Go module 搭建最小项目。
- 使用 `main.go` 支持在项目根目录直接执行 `go run .`。
- 使用 `cmd/cohert/main.go` 保留标准 CLI 二进制入口，方便后续 `go build -o cohert ./cmd/cohert`。
- 按职责拆分为 `internal/cli`、`internal/app`、`internal/agent`、`internal/llm`、`internal/tools`。

关键改动：

- 新增 CLI 入口和根入口。
- 新增 Agent Runner。
- 新增 OpenAI-compatible LLM Client。
- 新增基础工具注册体系和文件/命令/询问类工具。
- 新增 `configs/config.yaml` 默认配置读取逻辑。

最终效果：

- 可以在项目根目录执行 `go run .` 进入交互模式。
- 可以执行 `go run . ask "任务"` 运行单次任务。
- Cohert 具备最小 Agent Loop：用户输入、模型流式输出、工具调用、工具结果回灌、继续下一轮。

验证方式：

- 本地启动主程序。
- 使用 DeepSeek API Key 运行真实命令行任务。
- 通过 `go test ./...` 验证当前 Go 包可编译。

后续影响：

- 后续 P0/P1 开发都围绕这个 CLI-first Runtime 继续扩展。
- UI、全局安装、复杂会话管理都不在 MVP 初始化阶段处理。

## 统一项目命名和文档口径

任务来源：

- 对应任务 ID：项目品牌和文档清理。
- 触发原因：项目需要作为独立项目 Cohert 存在，文档和描述中不能留下旧项目痕迹。

为什么这样开发：

- 项目名称、命令名、文档描述必须统一，否则后续用户理解和安装命令都会混乱。
- 独立项目需要自己的表述，不应该让 README 和学习文档看起来像迁移说明。

技术路径：

- 将项目描述统一为 Cohert。
- 删除文档中关于旧项目、重写来源、临时命名的描述。
- 将启动方式统一为 `go run .` 和 `go run . ask "任务"`。
- 暂不做全局命令安装，避免把未确认方案写进用户文档。

关键改动：

- 更新 `README.md`。
- 更新 `docs/learning.md`。
- 更新 `docs/testing.md`。
- 保留 `cmd/cohert` 作为正式命令入口。

最终效果：

- 用户看到的是一个独立的 Cohert 项目。
- 本地测试文档只描述当前已经实现的启动方式。
- 全局启动方案没有进入当前文档，避免误导。

验证方式：

- 检查文档中的项目命名和启动命令。
- 确认 `go run .` 可以从项目根目录启动。

后续影响：

- 后续所有新增文档、代码注释、命令输出都应使用 Cohert 这个名称。

## 补齐运行状态和工具名常量

任务来源：

- 对应任务 ID：P0-001、P0-002。
- 触发原因：运行状态和工具名原本散落在代码中，后续维护容易拼错，也不利于测试稳定识别。

为什么这样开发：

- Agent 的运行状态属于核心协议，不应该用裸字符串到处写。
- 工具名是模型调用工具时的关键标识，必须集中管理。
- 常量集中后，后续新增工具、重命名工具、写测试都会更稳。

技术路径：

- 在 `internal/agent/types.go` 定义运行状态常量。
- 在 `internal/tools/registry.go` 定义工具名常量。
- 替换 Runner 和工具注册里的裸字符串。

关键改动：

- 新增 `RunStatusDone`。
- 新增 `RunStatusExited`。
- 新增 `RunStatusMaxTurnsExceeded`。
- 新增 `ToolNameFileRead`、`ToolNameFileWrite`、`ToolNameFilePatch`、`ToolNameCodeRun`、`ToolNameAskUser`。

最终效果：

- Runner 返回状态时使用常量。
- 工具注册和 unknown tool 提示使用统一工具名。
- 后续测试可以直接对常量断言。

验证方式：

- 执行 `go test ./...`。
- 运行主程序确认状态常量替换没有破坏流程。

后续影响：

- 新增工具时必须先补工具名常量，再注册工具。
- 新增运行状态时必须先在 `internal/agent/types.go` 定义。

技术路径：

- 构造假的 SSE 文本流。

- 验证文本片段会正确拼成最终内容。
- 验证工具调用的名称和 JSON 参数可以跨分片拼接。

关键改动：

- 新增 `internal/llm/openai_test.go`。
- 新增 `TestParseOpenAISSEText`。
- 新增 `TestParseOpenAISSEToolCalls`。

最终效果：

- 文本流式解析有单元测试保护。
- tool_calls 分片拼接有单元测试保护。
- 后续改 OpenAI Client 时更容易发现协议回归。

验证方式：

- 执行 `go test ./...`。

后续影响：

- 后续支持更多模型协议时，也应补协议解析测试。
- 真实端到端测试和单元测试要分开看，不能只靠终端肉眼观察。

## 统一工具错误返回格式

任务来源：

- 对应任务 ID：P0-030、P0-032。
- 触发原因：工具失败、未知工具、坏 JSON 参数需要用稳定结构回灌给模型，帮助模型自我修正。

为什么这样开发：

- 如果工具错误只是普通字符串，模型很难稳定识别错误类型和下一步动作。
- 测试也很难基于普通字符串做准确断言。
- 统一结构可以同时服务模型、日志和单元测试。

技术路径：

- 在 `internal/agent/types.go` 定义 `ToolErrorData`。
- 使用 `status/code/message/hint` 作为统一错误结构。
- 在 Runner 参数解析失败时返回 `bad_json`。
- 在工具执行失败时返回 `tool_run_failed`。
- 在工具不存在时返回 `unknown_tool` 和可用工具列表。

关键改动：

- 新增 `ToolStatusSuccess`、`ToolStatusError`。
- 新增 `ToolErrorData`。
- 新增 `NewToolError`。
- 修改 Runner 中的 bad JSON 处理逻辑。
- 修改工具和 registry 的错误返回。

最终效果：

- 工具错误变成可机器识别的结构化数据。
- 模型看到错误后能根据 `hint` 重新生成参数或选择正确工具。
- 坏 JSON 不再静默变成空参数。

验证方式：

- 执行 `go test ./...`。
- 检查 Runner 中 bad JSON 分支会回灌结构化错误。

后续影响：

- 后续所有工具错误都应优先返回 `ToolErrorData`。
- 新增错误类型时要补明确的 `code` 和中文 `hint`。

## 定义 Session 数据结构和本地存储层

任务来源：

- 对应任务 ID：P0-010、P0-011。
- 触发原因：后续需要支持会话列表和恢复上下文，必须先定义本地 session 数据结构和文件路径约定。

为什么这样开发：

- 要实现 resume，必须先决定 session 元信息和消息历史分别怎么存。
- `meta.json` 和 `history.jsonl` 分开，可以让会话列表读取更快，也让消息追加更简单。

技术路径：

- 新建 `internal/session` 包。
- 定义 `Session` 保存会话元信息。
- 定义 `HistoryEntry` 保存单条消息历史。
- 定义 `Store` 统一管理目录和路径。
- 默认目录使用 `temp/sessions`，避免 MVP 阶段写入全局 HOME。

关键改动：

- 新增 `internal/session/types.go`。
- 新增 `internal/session/store.go`。
- 新增 `internal/session/store_test.go`。
- 定义 `DefaultRootDir`、`MetaFileName`、`HistoryFileName`。
- 定义 `NewID` 生成带时间前缀的 session ID。

最终效果：

- 可以创建 session 目录。
- 可以写入 `meta.json`。
- 可以稳定计算 `history.jsonl` 路径。
- session 字段和后续 resume 需要的数据结构已经确定。

验证方式：

- 执行 `go test ./...`。
- 单测验证 `Store.Create` 会写入 `meta.json`。
- 单测验证 `HistoryPath` 的路径约定稳定。

后续影响：

- 后续 P0-012 可以直接基于 `Store` 写入 `history.jsonl`。
- 后续 P0-014 可以基于 `HistoryEntry` 恢复 `Runner.history`。

## Runner 写入 history.jsonl

任务来源：

- 对应任务 ID：P0-012。
- 触发原因：Runner 已经有内存 `history`，但还没有把 user/assistant/tool 消息落盘，无法支持进程退出后的上下文恢复。

为什么这样开发：

- 会话恢复的基础是完整保存每一轮消息。
- 写入时机必须靠近 Runner 追加内存 history 的位置，否则容易出现“内存有、文件没有”的不一致。
- Runner 不应该自己拼路径和写 JSON 文件，文件组织交给 `session.Store`。

技术路径：

- 在 `session.Store` 中新增 `AppendHistory`，负责追加一行 `HistoryEntry` 到 `history.jsonl`。
- 在 `session.Store` 中新增 `LoadMeta`，用于刷新和读取 session 元信息。
- 在 `agent.Runner` 中新增 `SessionStore`、`SessionCWD`、`SessionModel`、`sessionID`。
- 在 Runner 中新增 `appendMessage`，统一维护内存 history 和本地 history。
- 在 Runner 第一次收到用户输入时创建 session，后续同一个 Runner 复用同一个 session。
- 在 `app.NewRunner` 中默认注入 `temp/sessions` 存储。

关键改动：

- 更新 `internal/session/store.go`。
- 更新 `internal/agent/runner.go`。
- 更新 `internal/app/app.go`。
- 新增 `internal/agent/runner_test.go`。
- 更新 `internal/session/store_test.go`。

最终效果：

- 每次用户输入会写入一条 `role=user` 历史。
- 模型最终回答会写入一条 `role=assistant` 历史。
- 模型调用工具时，assistant 的 `tool_calls` 消息会先写入。
- 每个工具执行结果会写入一条 `role=tool` 历史。
- `history.jsonl` 使用一行一个 JSON，方便追加和后续读取恢复。

验证方式：

- 执行 `gofmt`。
- 执行 `go test ./...`。
- `internal/session` 测试验证 `AppendHistory` 会写入 JSONL。
- `internal/agent` 测试验证 Runner 执行后会生成 `meta.json` 和 `history.jsonl`。

后续影响：

- P0-014 可以继续读取 `history.jsonl`，把消息还原进 `Runner.history`。
- P0-013 可以读取 `meta.json` 和 `history.jsonl` 行数实现 session list。
- `/clear` 当前会清空内存 history 并重置 sessionID，后续如果要保留旧 session，需要再设计清理语义。

## 按 GA 思路稳住 code_run 执行器

任务来源：

- 对应任务 ID：P0-060、P0-061、P0-062、P0-063、P0-064、P0-065、P0-066。
- 触发原因：用户在交互模式里询问 session 效果时，模型调用 `code_run` 执行了大范围递归搜索，导致终端长时间卡住；同时 `bash -lc` 加载了用户 shell 配置，输出了 `.bashrc` 中 `tldr completion bash` 的崩溃噪音。

为什么这样开发：

- 用户明确要求先照 GA 的 `code_run` 思路做，不要在 tool 调用外面额外加一层 command guard。
- 当前阶段优先把执行器本身做稳，比提前抽象安全策略更直接。
- GA 的 `code_run` 使用 `bash -c`、默认 60 秒 timeout、输出截断，这些点适合 Cohert 借鉴。
- Cohert 保留自己的结构化结果优势，把 timeout 作为字段返回，而不是只写到 stdout。

技术路径：

- Unix/macOS 下把 `bash -lc` 改成 `bash -c`。
- 保留 60 秒默认 timeout。

## 实现浏览器 CDP 点击与输入链路

任务来源：

- 用户要求按以下顺序继续开发浏览器操作能力：
  - 插件 cdp command。
  - Go 层 `browser_cdp`。
  - `browser_click`。
  - `browser_click_element`。
  - `browser_type`。
  - `browser_type_element`。
  - 页面变化监控。
- 用户要求开发记录文档必须写清楚每一步的技术原因和实现方式。

为什么这样开发：

- 现有 Cohert 已具备 `browser_tabs`、`browser_open`、`browser_scan`、`browser_execute_js`，但只能读取页面和执行 JS。
- 普通 JS 的 `element.click()` 或 `dispatchEvent` 会产生 `isTrusted=false` 的合成事件，很多登录、支付、文件上传、自定义下拉框会拒绝这类事件。
- 浏览器真实交互应该走 CDP 的 `Input.dispatchMouseEvent`、`Input.insertText` 等输入协议。
- JS 仍然有价值，但它的职责应该是读取 DOM、滚动元素、计算 `getBoundingClientRect()`，而不是直接伪造点击。
- 如果动作工具只返回“success”，模型无法判断页面是否真的变化，容易重复点击或盲目继续，所以必须补轻量页面变化监控。

总体分层：

```text
模型工具调用
  -> internal/tools 解析和校验参数
  -> internal/browser.Client 稳定接口
  -> internal/browser.Bridge WebSocket 命令
  -> Chrome 插件 background.js
  -> chrome.debugger / chrome.scripting
  -> 用户真实 Chrome 标签页
```

### 第一步：插件 cdp command

开发内容：

- 在 `assert/cohert_browser_bridge/background.js` 中新增 `cdp` command。
- 新增 `withDebugger(tabId, fn)`，统一管理 `chrome.debugger.attach` 和 `detach`。
- 新增 `sendDebuggerCommand(target, method, params)`，封装 `chrome.debugger.sendCommand`。
- 新增 `handleCDP(request)`，负责解析 `method`、`params`、`tab_id` 并返回原始 CDP 结果。

关键实现：

```text
resolveTabId
  -> collectLightSnapshot
  -> chrome.debugger.attach
  -> chrome.debugger.sendCommand
  -> chrome.debugger.detach
  -> collectLightSnapshot
  -> buildLightDiff
```

为什么用 `finally detach`：

- Chrome debugger attach 后会占用 tab 的调试通道。
- 如果动作失败时不 detach，后续动作可能因为 debugger 状态异常而失败。
- detach 失败通常意味着 tab 已关闭或正在跳转，因此不能覆盖原始动作错误。

### 第二步：Go 层 browser_cdp

开发内容：

- 在 `internal/browser/types.go` 中新增 `CDPResult`。
- 在 `browser.Client` 接口中新增 `CDP` 方法。
- 在 `internal/browser/server.go` 中新增 `Bridge.CDP`，通过 WebSocket 发送 `command=cdp`。
- 在 `internal/browser/unavailable.go` 中补齐不可用客户端实现。
- 在 `internal/tools/browser_tools.go` 中新增 `BrowserCDP` 工具。
- 在 `internal/tools/registry.go` 和 `internal/app/app.go` 中注册 `browser_cdp`。

工具参数：

```json
{
  "tab_id": "可选",
  "method": "Runtime.evaluate",
  "params": {},
  "no_monitor": false
}
```

设计取舍：

- `browser_cdp` 不限制 method，因为它是底层调试工具。
- 常规点击和输入不鼓励直接使用 `browser_cdp`，否则模型容易拼错三段鼠标事件。
- 高频交互必须用更上层的 `browser_click` 和 `browser_type` 封装。

### 第三步：browser_click

开发内容：

- 在 `browser.Client` 中新增 `Click` 方法。
- 在 `Bridge` 中新增 `Click`，发送 `command=click`。
- 插件侧新增 `clickTab(request)`。
- 工具层新增 `BrowserClick`。

插件侧点击序列：

```text
Page.bringToFront
Input.dispatchMouseEvent mouseMoved(0, 0)
Input.dispatchMouseEvent mouseMoved(x, y)
Input.dispatchMouseEvent mousePressed(x, y, button=left, clickCount=1)
Input.dispatchMouseEvent mouseReleased(x, y, button=left, clickCount=1)
```

关键细节：

- `x/y` 是 viewport 坐标，不是屏幕物理坐标。
- 坐标来源应优先是 `getBoundingClientRect()`。
- 三个鼠标动作必须在同一次 debugger attach 生命周期内完成。
- 点击完成后短暂等待，再做轻量快照，用于判断页面是否变化。

为什么要有 `mouseMoved(0, 0)`：

- 首次 debugger attach 可能让 Chrome 出现调试提示条或触发布局变化。
- 预热动作可以让后续输入链路更稳定。
- 对 `browser_click_element` 来说，元素 rect 是在点击前即时测量的，因此不会长期复用旧坐标。

### 第四步：browser_click_element

开发内容：

- 工具层新增 `BrowserClickElement`。
- 新增 `locateElementRect`，通过 `browser_execute_js` 执行定位脚本。
- 定位脚本会执行 `querySelector`、`scrollIntoView`、`requestAnimationFrame`、`getBoundingClientRect`。
- Go 层计算中心点后调用 `client.Click`。

定位脚本的职责：

```text
找到 selector
滚动到 viewport 中央
等待一帧让布局稳定
读取 rect
检查 width/height/display/visibility
返回 rect
```

为什么不在 JS 里 click：

- JS click 是合成事件，`isTrusted=false`。
- 工具目标是模拟真实用户操作。
- 因此 JS 只负责“看”和“算”，CDP 负责“动”。

### 第五步：browser_type

开发内容：

- 在 `browser.Client` 中新增 `Type` 方法。
- 在 `Bridge` 中新增 `Type`，发送 `command=type`。
- 插件侧新增 `typeInTab(request)`。
- 工具层新增 `BrowserType`。

输入流程：

```text
Page.bringToFront
如果 clear=true：
  Input.dispatchKeyEvent Cmd+A
  Input.dispatchKeyEvent Backspace
Input.insertText(text)
```

为什么选择 `Input.insertText`：

- 它比 JS 直接设置 `value` 更接近真实输入。
- 对 React、Vue 等框架，真实输入链路更容易触发状态同步。
- 相比逐字符构造 keyDown/keyUp，`Input.insertText` 更简单稳定，适合第一版。

### 第六步：browser_type_element

开发内容：

- 工具层新增 `BrowserTypeElement`。
- 复用 `locateElementRect` 获取目标输入框 rect。
- 先调用 `client.Click(..., noMonitor=true)` 聚焦输入框。
- 再调用 `client.Type(..., noMonitor=用户参数)` 输入文本。

为什么聚焦点击不返回 diff：

- `browser_type_element` 是一个语义工具，用户关心的是“输入后页面变化”。
- 聚焦只是输入前置动作，如果也返回一段 diff，会让模型看到两段变化信号。
- 因此聚焦点击禁用监控，最终由输入动作统一返回 diff。

### 第七步：页面变化监控

开发内容：

- 插件侧新增 `collectLightSnapshot(tabId)`。
- 插件侧升级 `buildLightDiff(before, after)`。
- `execute_js`、`cdp`、`click`、`type` 都支持 `no_monitor`。

快照字段：

```text
tab.url
tab.title
当前可脚本化 tab 数量
document.body.innerText.length
可交互元素数量
document.activeElement 摘要
```

为什么只做轻量 diff：

- 完整 DOM diff 很容易产生巨大工具结果。
- 第一版目标是让模型知道动作是否生效，而不是重建网页结构。
- `browser_scan` 已经负责读取页面正文，动作工具只需要返回变化摘要。

返回示例：

```text
url changed
body text length 1024->1400
interactive elements 18->20
focus INPUT[name=q]->BUTTON
tab count 1->2
```

关键改动：

- 更新 `assert/cohert_browser_bridge/background.js`：
  - 新增 `cdp` command。
  - 新增 `click` command。
  - 新增 `type` command。
  - 新增 debugger attach/detach 封装。
  - 新增轻量页面变化快照和 diff。
- 更新 `internal/browser/types.go`：
  - 新增 `CDPResult`、`Point`、`Rect`、`ClickResult`、`ElementClickResult`、`TypeResult`、`ElementTypeResult`。
  - 扩展 `Client` 接口。
- 更新 `internal/browser/server.go`：
  - 新增 `CDP`、`Click`、`Type`。
- 更新 `internal/browser/unavailable.go`：
  - 补齐新接口的不可用实现。
- 更新 `internal/tools/browser_tools.go`：
  - 新增 `BrowserCDP`、`BrowserClick`、`BrowserClickElement`、`BrowserType`、`BrowserTypeElement`。
  - 新增 selector 定位和 rect 解析逻辑。
- 更新 `internal/tools/registry.go`：
  - 新增工具名常量。
  - 新增 schema 辅助函数。
  - 调整工具 schema 输出顺序。
- 更新 `internal/tools/args.go`：
  - 新增 float 和 object 参数解析。
- 更新 `internal/app/app.go`：
  - 注册新浏览器工具。
  - 更新系统提示词，让模型优先使用 DOM/JS 定位和 CDP 输入。
- 更新测试：
  - `internal/browser/server_test.go` 覆盖 `cdp`、`click`、`type` WebSocket 命令。
  - `internal/tools/browser_tools_test.go` 覆盖 `browser_cdp`、`browser_click`、`browser_type` 工具调用。
- 更新 `docs/ga_browser_technical_route.md`：
  - 记录浏览器输入链路落地状态。

最终效果：

- Cohert 已具备从“读取页面”到“真实点击和输入”的第一版闭环。
- selector 点击和 selector 输入遵循“JS 定位、CDP 动作”的边界。
- 动作工具会返回轻量页面变化摘要。
- OCR 仍然只作为后续兜底，不进入普通网页主链路。

验证方式：

后续影响：

## 实现浏览器等待链路

任务来源：

- 用户反馈 Cohert 有时打开网页后，网页还没加载出来，Agent 就开始改方案，体验很差。
- 这个问题的根因不是“不会打开网页”，而是缺少“打开后等待页面到位”的工具链路。

为什么这样开发：

- 现代网页大量内容由前端 JS 异步渲染。
- `chrome.tabs.create` 或 `chrome.tabs.update` 返回后，页面可能还在白屏、骨架屏、loading 或局部请求中。
- 即使 `tab.status == complete`，SPA 页面也可能还在继续渲染正文和结果列表。
- 如果 Agent 在这些状态下立刻 `browser_scan`，就会读到半成品页面，然后误判“没有结果”“没有按钮”“页面打不开”，进而换方案。

目标行为：

```text
错误链路：
browser_open -> browser_scan -> 页面没出来 -> 误判 -> 改方案

正确链路：
browser_open -> browser_wait_for_load -> browser_wait_for_stable -> browser_scan
```

点击或输入后的正确链路：

```text
browser_click_element / browser_type_element
  -> browser_wait_for_selector / browser_wait_for_text / browser_wait_for_stable
  -> browser_scan 或继续操作
```

### 第一步：插件 wait command

开发内容：

- 在 `assert/cohert_browser_bridge/background.js` 中新增统一 `wait` command。
- 新增 `sleep(ms)`，用于插件侧轮询。
- 新增 `normalizeWaitTiming(request)`，统一处理 `timeout_ms` 和 `interval_ms`。
- 新增 `readPageState(tabId)`，读取页面轻量状态。
- 新增 `waitForCondition(tabId, timing, check)`，统一轮询骨架。
- 新增四个具体等待实现：
  - `waitForLoad`
  - `waitForSelector`
  - `waitForText`
  - `waitForStable`
- 在 `handleCommand` 中接入 `command === "wait"`。

为什么等待放在插件侧：

- 插件能直接调用 `chrome.tabs.get(tabId)` 读取 `tab.status`。
- 插件能通过 `chrome.scripting.executeScript` 读取页面 DOM。
- 如果 Go 侧轮询，每次检查都要经过 WebSocket 请求，延迟和协议复杂度更高。
- wait 作为一个插件 command 返回一次结果，更适合模型理解。

为什么 timeout 不直接抛错：

- 超时不一定是系统错误，也可能只是页面没有出现目标状态。
- 返回 `status: "timeout"` 能让模型知道“已经等过了但没等到”。
- 真正的协议错误仍然通过 WebSocket error 返回，例如 tab 不可用、selector 参数为空。

### 第二步：browser_wait_for_load

用途：

- 等页面基础加载完成。
- 主要放在 `browser_open` 后，或者点击链接导致页面跳转后。

判断条件：

```text
chrome.tabs.get(tabId).status == complete
document.readyState == interactive 或 complete
```

返回字段：

```json
{
  "status": "success",
  "mode": "load",
  "matched": true,
  "ready_state": "complete",
  "tab_status": "complete",
  "url": "...",
  "title": "..."
}
```

解决的问题：

- 页面还在白屏时不要扫描。
- 页面刚跳转时不要立刻判断失败。
- 打开搜索页、文档页、登录页后先等基础 DOM 到位。

### 第三步：browser_wait_for_selector

用途：

- 等某个元素出现、可见、隐藏或消失。

参数：

```json
{
  "tab_id": "可选",
  "selector": ".result-item",
  "state": "attached|visible|hidden|detached",
  "timeout_ms": 10000,
  "interval_ms": 200
}
```

状态含义：

```text
attached  querySelector 能找到元素
visible   元素存在，rect 宽高大于 0，且 display/visibility/opacity 可见
hidden    元素存在但不可见
detached  querySelector 找不到元素
```

解决的问题：

- 搜索结果列表还没渲染时，不要判断“没有结果”。
- 弹窗还没关闭时，不要继续点击后面的按钮。
- 按钮还没出现时，不要直接改用别的策略。

### 第四步：browser_wait_for_text

用途：

- 等页面正文中出现某段文字。

参数：

```json
{
  "tab_id": "可选",
  "text": "提交成功",
  "timeout_ms": 10000,
  "interval_ms": 200
}
```

适合场景：

- 等“登录成功”。
- 等“提交成功”。
- 等“验证码已发送”。
- 等搜索结果关键词出现。

为什么它和 selector 都需要：

- 有些页面结果没有稳定 selector，但有明确文案。
- 有些页面文案可能变化，但结构 selector 稳定。
- 两者互补，模型可根据任务选择。

### 第五步：browser_wait_for_stable

用途：

- 等页面轻量状态稳定一段时间。
- 这是不知道该等哪个 selector 或 text 时的通用兜底。

判断字段：

```text
tab status
document.readyState
url
title
body.innerText.length
可交互元素数量
```

参数：

```json
{
  "tab_id": "可选",
  "stable_ms": 800,
  "timeout_ms": 10000,
  "interval_ms": 200
}
```

设计取舍：

- 不比较完整 DOM，避免性能和返回内容过大。
- 不要求正文完全不变很久，默认只需要短时间稳定。
- 这是 scan 前的稳定性保险，不替代 `browser_scan`。

### 第六步：Go 层 Wait 接口

开发内容：

- 在 `internal/browser/types.go` 中新增 `WaitResult`。
- 在 `browser.Client` 中新增 `Wait` 方法。
- 在 `internal/browser/server.go` 中新增 `Bridge.Wait`。
- 在 `internal/browser/unavailable.go` 中补齐不可用实现。
- 将 `defaultCommandTimeout` 调整为更长时间，避免 wait 工具本身还没超时，Go bridge 先超时。

为什么使用一个底层 `Wait` 接口：

- 插件协议只需要一个 `command=wait`。
- Go 工具层可以拆成多个语义工具。
- 后续新增 `browser_wait_for_url` 时，可以复用同一个底层接口。

### 第七步：Go 工具层四个语义工具

新增工具：

```text
browser_wait_for_load
browser_wait_for_selector
browser_wait_for_text
browser_wait_for_stable
```

为什么不直接暴露一个 `browser_wait`：

- 模型更容易理解“等加载”“等元素”“等文字”“等稳定”。
- 工具描述可以明确写出使用场景。
- 参数校验更清楚，例如 selector 必填、text 必填。

新增辅助函数：

```text
runBrowserWait
```

它负责统一读取：

```text
tab_id
timeout_ms
interval_ms
```

然后调用：

```text
client.Wait(ctx, tabID, mode, params, timeoutMS, intervalMS)
```

### 第八步：系统提示词更新

系统提示词已更新浏览器流程：

```text
网页查询优先 browser_open -> browser_wait_for_load -> browser_wait_for_stable -> browser_scan
浏览器点击、输入、跳转或异步操作后，必须先等待 load、selector、text 或 stable，再判断失败
```

这一步很重要，因为工具存在并不代表模型一定会用。系统提示词必须把“先等再判断”变成默认策略。

关键改动：

- 更新 `assert/cohert_browser_bridge/background.js`：
  - 新增 wait command。
  - 新增 load、selector、text、stable 四种等待模式。

最终效果：

- Cohert 不应该在页面还没加载出来时立刻 scan 并误判。
- 打开网页后的默认链路变成 `open -> wait load -> wait stable -> scan`。
- 点击、输入、跳转后的默认链路变成 `action -> wait -> scan/continue`。
- 如果等不到目标状态，工具返回 timeout，模型能基于 timeout 做下一步判断。
